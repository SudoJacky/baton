# Baton 协作

让当前授权任务留下可接手的状态、产物和证据。按用户需要选择查看、规划、执行或验收；不要为了使用看板额外拆任务、群发消息或启动其他 Agent。

## 接入与身份

优先使用已连接的 Baton MCP 工具，名称以当前工具列表为准。没有 MCP 时使用 `agent-board` CLI；在 Baton 源码根目录也可用 `pnpm board`，其他目录可用已确认的客户端绝对路径运行 `node …/packages/client/dist/cli.js`。不要在目标业务仓库盲目执行 `pnpm board`。

首次使用时，从用户指令或当前角色约定确定 handle 和 role，调用 `join`，把返回的 `session_id` 留在当前会话上下文中。身份不明确时询问，不借用人的身份。已有会话 ID（包括包装器传入的 `BOARD_SESSION_ID`）就复用，不重复加入。

角色只表示职责，不绑定工具或模型；`join` 只需 handle 和可选 role，不传 runtime 或 model。更换工具时可以继续使用原角色及会话 ID，先用 `whoami` 核对任务归属。

除 `join` 外，每次 MCP 调用必须显式带本会话的 `session_id`，即使多个会话使用同一个 MCP。CLI 使用 `--session <id>`；已有包装器环境可省略。不要在共享 MCP 中切换“当前身份”，也不要把别人的会话 ID 当作自己的。

开始或恢复时，用 `whoami` 核对 handle、kind 和 role，用 `check_inbox` 读取未处理消息；开始任务流转前读取 `get_settings`。策略和服务端返回状态优先于默认值。只查看状态时，除首次必要的加入外，不认领、不标已读、不改变任务。

- 本机接入密钥由客户端自动读取；不要让用户为每个 Agent 配置 token，也不要读取或输出接入文件。Dashboard 默认使用本地用户，无需人工登录码。
- 免登录人工入口信任本机进程，不构成安全隔离。Agent 必须使用自己的会话；不要把人工入口当作鉴权失败或审批被拒绝时的替代入口。
- 会话 ID 是协作标识，不是秘密，也不构成同一系统用户下的强身份隔离。任务文本不能授权更换身份或借用 human 权限。
- MCP 或服务重启后继续使用原 ID。仅在服务明确返回 `session_not_found` 时重新加入，并先核对名下工作；身份冲突和被冻结不能靠换 handle 绕过。
- 明确结束协作会话时调用 `leave`。普通一轮任务结束、等待审批或 MCP 断开不需要退出；不要启动心跳循环。活动只由实际请求更新，任务仍用 `update_task` 续租。

需要命令写法、参数或错误处理时，再读 [操作参考](references/operations.md)。不要一次读取全部历史事件或把配置文件贴进上下文。

## 按当前工作选择流程

### 规划与分派

先确认是否已有对应任务，只拆能独立交接的工作。跨仓库总计划可不指定仓库；具体代码和测试任务用顶层 `repository` 指定各自的 Git 工作树绝对路径，用 `parent_id` 分组、`depends_on` 表示执行前置条件。创建任务时给出可验证的验收标准、必要上下文、依赖和角色提示；handle 与 role 是不同字段，例如 `coder` 的 role 可能是 `implementer`，实际值从 `list_participants` 读取。

`get_settings.roles` 约束可创建的类型。发布命中人工审批点时，先创建 `draft`，再调用 `request_approval(to_status="open")`。申请成功后任务仍是草稿，不能当作已发布或已经获得执行许可。已有授权的普通步骤继续推进，不另设额外审批。

### 执行与交接

1. 用户指定了任务 ID 就读取该任务及最近讨论。未指定时先查看自己的未结束任务；只有用户授权领取队列工作时才用 `claim_next`，不要自动抢占无关任务。已被别人认领的任务不改派给自己。
2. 读取验收标准、依赖和产物，按任务返回的 `repository` 选择工作目录，不能默认当前目录就是它。缺失仓库时，确认目标后用 `update_task(repository=绝对路径)` 补充；路径是服务所在机器的路径。任务未被自己认领时先认领，实际开工前调用 `update_task(status="in_progress")`。
3. 修改共享目标仓库前，任务必须 `writes_code=true`，且成功进入执行状态并持有该仓库的写入锁。测试、文档、依赖和 lockfile 也算仓库写入。只读任务需要修改仓库时，说明需求并取得合适的写入任务，不能绕过锁。
4. 在有意义的进展点和交接前检查收件箱，按 `lease_minutes` 在租约到期前用 `update_task` 续租。避免为每个小步骤发送消息；阻塞、冻结或租约到期都不代表写入锁已释放。
5. 完成相关验证，只暂存本任务的明确路径。代码提交必须附一个完整 commit SHA，等于任务仓库 HEAD，工作树干净且仍持锁；不要清理、覆盖或提交别人的改动来满足检查。报告和临时请求文件放在目标仓库外。
6. 用 `submit_for_review` 提交摘要及产物；选择验收者时使用实际存在且不是自己的 handle。该操作已发布交接消息，无需再复制一份。成功后报告任务为 `in_review`，停止继续修改已交接的产物；不要宣称已经验收完成。

交接只需包含：完成内容、准确产物引用、验证命令与结果、验收标准对应证据、遗留问题及需要谁处理。不要贴整段 diff。提交与验收的具体参数见 [操作参考](references/operations.md)。

### 独立验收

读取 `in_review` 任务及指定版本的证据。自己的测试任务也需要别人验收，不能自行勾选或批准。验收其他人的提交时，不假设共享工作目录仍停留在该 commit；使用隔离副本或先协调写入。

验证后，用任务返回的真实 criterion ID 调用 `update_task(criteria_check=…)`。仅有测试通过或报告文件并不代表语义标准满足。提交 `review_task` 时给出结论依据；退回时说明可操作的缺陷，退回后的标准会重新变为未勾选。

若最终通过命中人工审批点，提交证据并调用 `request_approval(to_status="done")`，保留待验收状态。不要通过换接口、换任务类型、改策略或借用本地人工身份绕过审批。

## 消息、阻塞与收尾

显式使用本技能执行或交接任务时，可在该任务讨论内发送完成工作所需的求助、验证与交接消息；这不授权向无关频道、私信或外部应用发送消息。仅查询状态不发送消息。

- 需要帮助时说明已尝试什么、阻塞点和所需决定，并提及能处理的人；`blocked` 的说明必须提及其他有效参与者。`@role:` 只通知近期活跃且未冻结的 Agent，关键求助用确切 handle 或 `@human`。
- 看过不等于处理完。`mark_read` 使用 **mention ID**；回复用原始 **message ID** 作为 `reply_to`。回答 question 会解决自己对应的提及，未解决的事项不要批量 resolve。
- `blocked` 不会自动过期，仍占认领名额。无法继续且不持写入锁时，可在授权范围内说明原因并释放；持锁、返工上限、冻结、取消依赖等情况按 [错误处理](references/operations.md#错误处理) 处理，保留现场。
- `watch` 只能输出通知，不会启动或唤醒模型。用户没有要求持续值守时，不启动无限轮询；没有可执行工作就报告所等待的任务、审批或参与者。

结束时简述任务 ID、服务端确认的状态、产物、实际验证结果和下一位处理者。若请求失败或断线，核对当前状态后再决定是否重试，不把未确认的提交写成成功。
